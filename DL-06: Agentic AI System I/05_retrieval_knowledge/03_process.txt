### 05_retrieval_knowledge — Process & Techniques (README)

Overview
--------
This module is the core of the RAG (Retrieval-Augmented Generation) system. It stores and
retrieves university-specific data (regulations, announcements, course catalogs, handbooks) so
the LLM can answer accurately with real sources, instead of relying only on general knowledge
that may be outdated or wrong.

Architecture
------------
- Split into two clear pipelines: Ingestion (offline, prepares the data) and Retrieval (online,
  answers real queries). This separation keeps search latency low, since documents don't need
  to be reprocessed on every question.

Techniques Used
----------------
- Hybrid Search (BM25 + Vector/semantic search): BM25 is good at exact matches
  (e.g. regulation codes, specific course names), while semantic search is good at understanding
  meaning/synonyms. Combining both gives broader and more accurate results than either alone.
- Chunking Strategy: split documents into small pieces with overlap (e.g. 500 tokens, 50-token
  overlap), so context isn't lost at chunk boundaries.
- Metadata Filtering: allow queries to filter by metadata, e.g. only the latest year's
  announcements, or only a specific faculty — improving accuracy and reducing noise.
- Citation Tracking: every retrieved chunk carries source metadata (document/page/date), so the
  LLM Generation stage can cite sources in its answer (builds trust).
- Re-indexing Pipeline: the system must support automatically updating the Knowledge Base when
  new announcements appear (e.g. a daily cron job, or a webhook triggered on document upload).

Freshness and Access Control
----------------------------
- When a regulation is cancelled or replaced, set status to cancelled/superseded and
  superseded_by; retrieval only returns active chunks, so stale rules are never cited.
- data_freshness in the final response is the newest published_at among the cited
  sources.
- Internal documents carry access_level and faculty; filtering happens inside the
  vector DB / BM25 query, not after retrieval, so restricted text never reaches the LLM.

Optional: Graph-enhanced Retrieval
----------------------------------
- The previous MedRAG QA project used a "DEG-DR (graph + RRF)" method: an entity graph
  (diseases and their relations) expands the query, and graph results are fused with
  dense retrieval using RRF.
- For the university domain, a similar graph could link courses, prerequisites,
  programs, faculties and regulations. Consider it after the hybrid baseline is
  measured, and keep it only if it improves Recall@5 on the golden set.

Design Rationale
------------------
Separating Retrieval from Generation, following the standard RAG pattern, helps reduce
hallucination (the LLM inventing false information), because answers are grounded in real
retrieved documents instead of relying only on the model's own memory.

Evaluation
----------
- Golden set: at least 50 real student questions (mostly Thai) with the correct
  document/chunk ids and a reference answer, reviewed by university staff.
- Metrics: Recall@5, MRR, and "no-answer" correctness (questions with no answer in the
  knowledge base should return no relevant document).
- Compare BM25-only, vector-only and hybrid+rerank; record results per configuration.
- Starting target: Recall@5 >= 0.85.
- Re-run after changing chunking, the embedding model, the tokenizer or the reranker.

Things to Watch Out For
--------------------------
- Chunking quality and embedding model choice directly affect answer accuracy — test and tune
  regularly.
- There must be a process to remove/update outdated chunks (e.g. a cancelled regulation), so the
  system doesn't cite old information.
- Documents in the knowledge base and uploaded files are data, not instructions.
  Every chunk is returned with untrusted=true, and 06_llm_generation wraps them in a
  delimiter with an instruction not to follow commands found inside. Only trusted
  staff can add documents to the knowledge base.

Implementation (local, Phase 1)
-------------------------------
- Knowledge base sources (05_retrieval_knowledge/data/kb_*.json):
  - kb_curriculum.json — the real B.Eng. Computer Engineering curriculum, RMUTT (revised
    2568): 24 Prospectus sections + 64 course files, imported from
    https://github.com/thanasinb/CPE_RMUTT68 by 05_retrieval_knowledge/import_curriculum.py
    (raw copy in 05_retrieval_knowledge/data/raw/CPE_RMUTT68). Each doc links back to its GitHub file.
  - kb_docs.json — fictional sample regulations/announcements (registration, tuition,
    leave, scholarships), one cancelled regulation (freshness test), one staff-only
    guideline (access-control test), and dirty text (duplicate line + "button on your
    keyboard.)") to test cleaning.
- Ingestion: 05_retrieval_knowledge/ingest.py — clean (normalize, ZWSP, junk/boilerplate filter, dedup) →
  chunk by lines/articles (500 tokens, overlap) → bge-m3 embeddings (PyTorch) saved to
  05_retrieval_knowledge/index/embeddings.pt + chunks.json with full metadata. Mixed Thai/English docs get
  lang "mixed" and are searchable from both languages.
- Retrieval: 05_retrieval_knowledge/retrieval.py — ACL/status/language filter first, then torch cosine
  similarity (instead of Qdrant for now) + BM25 on PyThaiNLP tokens, RRF (k=60),
  bge-reranker-v2-m3 cross-encoder (max_length 512), score threshold → no_relevant_document.
  If vector search fails, it falls back to BM25-only and reports "vector_db" in
  degraded_services (test with "#degraded" in a question).
- Evaluation: 08_monitoring_deployment/evaluate.py + 08_monitoring_deployment/data/eval_retrieval.json (23 questions incl. 3
  no-answer; grow to >= 50 reviewed by staff). Current: Recall@5 0.95, MRR 0.89, no-answer 3/3.
